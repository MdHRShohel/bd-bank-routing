# The routing number is not in the branch row -- it is inside each branch's
# expandable DETAIL block, as a `Routing No` label row in a nested table. Name is
# taken from the OUTER row's first cell and routing from that row's own nested
# table, so the pair stays within one branch (RULE 0).
# A BRANCH CAN LIST TWO ROUTING NUMBERS. 33 of them print
#   "<own routing>,160270817 (For Islamic Window)" -- and it is the SAME second
#   number every time. 160270817 is NCC's single Islamic-banking-window routing,
#   shared across those branches, not a per-branch one. Only the FIRST number is
#   taken as the branch's routing. 160270817 itself is NOT added: the bank does
#   not list it as a branch and it belongs to no one branch. It IS, however, a
#   real payable BEFTN destination, and leaving it out meant an employee whose
#   NCC account is at the Islamic window could select nothing and had to hand-type
#   a nine-digit routing through the manual escape hatch -- the one place a typo
#   silently redirects a salary. So it is stored ONCE as
#   `NCC ISLAMIC BANKING WINDOW`, named as a window rather than a branch, in the
#   district its own routing digits give (27 = DHAKA, which is what all 17 of
#   NCC's other 16027* branches carry). Storing it per-branch would instead have
#   collided 33 rows onto one routing. See BANK-NCC-ISLAMIC-WINDOW-1.
# TWO BRANCHES PUBLISH NO ROUTING AT ALL -- Chatkhil Branch and Kaligonj Branch
#   are listed with addresses and phones but no `Routing No` value. They are not
#   added; a routing cannot be invented.
# NO SETTLEMENT ENDPOINTS in their listing. OURS carried two, 160270004
#   TRUNCATION POINT and 160272686 HEAD OFFICE; both are removed.
# Districts are DERIVED from routing digits 4-5. A trailing ", <District>" is
#   stripped from a name only when the tail really is a district.
